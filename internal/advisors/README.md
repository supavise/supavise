# internal/advisors

The Security and Performance Advisors: the lints Studio's Advisors pages, `supabase db advisors`
and the MCP server's `get_advisors` show, computed on demand for one project. The routes are in
`internal/api/advisors.go` and `advisors_exceptions.go`; this package holds the engine. The user
guide is "Check a project with the advisors" in `docs/guide.md`.

```go
var r advisors.Runner                                  // zero value is usable; one per server
lints, err := r.SQL(ctx, ref, "public,graphql_public", exec) // []advisors.Lint, shared and cached for 10 s
lints = append(lints, advisors.ConfigLints(authSettings)...)
lints = advisors.Visible(lints, rules, userID)         // the Advisor Rules page's exceptions
security := advisors.Filter(lints, advisors.CategorySecurity)
r.Invalidate(ref)                                      // after a statement that changed the schema
```

## Where the lints come from

**The SQL lints** are the query Studio runs in its own self-hosted mode: `getLintsSQL` in
`packages/pg-meta/src/sql/studio/advisor/lints.ts` of `supabase/supabase` (Apache-2.0), wrapped by
Studio's `enrichLintsQuery` (`user: self host`). `lints.sql` holds it, generated by `gen/main.go`
from that file at the commit recorded in its header. Nothing is copied from `supabase/splinter`,
whose repository has no license.

The generator evaluates the TypeScript template the way Studio's `safeSql` tag does: JavaScript
escapes are cooked (so `\`` is a backtick and `\_` is `_`), `${literal(`...`)}` becomes a quoted
string with `docsUrl` replaced by `https://supabase.com/docs`, and any other `${...}` stops the run.
To refresh after a Studio bump:

```sh
git -C <supabase checkout> show <commit>:packages/pg-meta/src/sql/studio/advisor/lints.ts > /tmp/lints.ts
go run ./internal/advisors/gen -src /tmp/lints.ts -commit <full 40-character commit> -out internal/advisors/lints.sql
```

`TestVendoredSQLMatchesTheStudioPin` fails when `studio.tag` of `internal/versions/versions.yaml`
(`<date>-sha-<short commit>`) no longer matches the commit in the header, so a Studio bump cannot
ship with the old lints. After regenerating, look at the diff: new lint names need no code, but the
tests that list names (`TestVendoredSQLIsGeneratedOutput`) show what changed.

`Query` adds Studio's preamble to the SQL, with three differences that keep the intent:
`set local statement_timeout = '30s'` bounds the run, `pg_stat_statements.track` is switched off
with `set local` (Studio sets the session; a pooled connection must not stay untracked), and
`set local pgrst.db_schemas` carries the project's PostgREST `db_schema` list, because several lints
read it with `current_setting` to know what the Data API exposes. The API runs the text as
`supabase_admin` through pg-meta, the role and path Studio's runner uses, and pg-meta returns the
rows of the last statement.

**The configuration lints** (`config.go`) are the findings hosted computes from project settings,
for the ones Supavise can: `auth_otp_long_expiry` and `auth_db_connections_absolute`. The names,
levels, categories and links are those of hosted's Management API specs and responses.
`auth_db_connections_absolute` is word for word what the Supabase CLI's recorded responses hold
(v2.120.0); `auth_otp_long_expiry`'s texts come from published advisor output, and the trigger of
both is Supavise's reading of the setting they name:

| Lint | Level, category | Reported when |
|---|---|---|
| `auth_otp_long_expiry` | WARN, security | the email provider is on and `mailer_otp_exp` is over 3600 seconds |
| `auth_db_connections_absolute` | INFO, performance | `db_max_pool_size_unit` is not `percent`; the detail names `db_max_pool_size` |

The lints read the effective setting. A new hosted project has `mailer_otp_exp` 3600 and
`db_max_pool_size` 10, and the CLI's recording of one answers `auth_db_connections_absolute` and
nothing else. Supavise starts at GoTrue's own 86400 and 5, so a new Supavise project also answers
`auth_otp_long_expiry` until its OTP expiry is an hour or less, and its connection detail says 5.
Moving the default belongs to the Auth settings (`internal/projectconfig`, and the unit's
environment so that GoTrue gets it); it would shorten the OTP of existing projects at their next
restart, so it is a separate decision.

Not computed, with the reason in `ConfigLints`: `auth_leaked_password_protection` and
`auth_insufficient_mfa_options` (the CLI's recording of a hosted project that is entitled to both
features answers neither while `password_hibp_enabled` is off and no MFA method is on, and the
rule behind them is unknown), the compliance checks (`ssl_not_enforced`, `log_connections_not_enabled`,
`network_restrictions_not_set`, `pitr_not_enabled`, `password_requirements_min_length`,
`auth_password_policy_missing`, `no_backup_admin`, `leaked_service_key`), `auth_otp_short_length`,
`auth_allow_anonymous_sign_ins` and `vulnerable_postgres_version`.

**The health checks** (`health.go`) are asked for by name through `POST /v2/projects/{ref}/advisors/run`.
They need the project's logs and metrics, which Supavise does not keep, so each answers
`advisor_check_unavailable`, a result Studio and the MCP server leave out of what they show. A
project that is not running answers `project_not_active`.

## Behavior

- **Rows pass through.** A lint is kept as the database produced it (`Lint.Raw`), so a field the
  spec does not list yet reaches the client; Studio links public buckets on `metadata.bucket_id`.
  Lints are not filtered to the names of the pinned spec: hosted returns names its spec lacks
  (`auth_db_connections_absolute`), and so do the vendored SQL's newer lints.
- **Category split.** `GET /v1/projects/{ref}/advisors/security` returns the lints whose
  `categories` include `SECURITY`, and `performance` those that include `PERFORMANCE`. Studio's
  `run-lints` returns all of them, and its pages split them the same way.
- **Cache.** `Runner` keeps the SQL result of a project for 10 seconds (`DefaultTTL`) and gives
  callers that arrive during a run the same run, so a dashboard whose widgets all ask costs the
  database one query. A failure is not kept, and entries past their TTL go when the next result is
  stored. A project has one run at a time and the node at most `MaxConcurrent` (4): `Invalidate`
  drops the entry and marks a run under way as stale, which finishes for the callers that joined
  it but is not kept, and a caller that arrives after it waits for that run and then shares one new
  run with the others that waited. The API calls `Invalidate` after a migration, after a statement
  that may change the schema (`create`, `alter`, `drop`, `grant`, `revoke`, `truncate`,
  `comment on`) that came through `database/query` or Studio's SQL editor (the JSON body is
  decoded first, because a line break is `\n` there), and when it deletes a project. A change
  made over a direct or pooler connection shows within the 10 seconds.
- **Time.** The query stops after 30 seconds in the database (`StatementTimeout`) and the API
  answers 504. A run is bounded by its own context and not by the first caller's, which may leave.
- **Rules.** `Exception` is a rule of the Advisor Rules page (a feature preview in Studio). A rule
  selects lints by name, category and metadata and hides them from the project or one member;
  `internal/registry` keeps them (migration `1450_advisor_exceptions.sql`).

## Postgres artifact

The Postgres artifact ships `index_advisor` 0.2.0 and `hypopg` 1.4.1 (`postgres-17.11.0.004-r1`: the
darwin archive's file list and the Linux SBOM both show them), and its configuration template lists
`pg_stat_statements` in `shared_preload_libraries` (read in the darwin archive). Studio's Query
Performance index advisor needs `index_advisor` and `hypopg` to be available, which they are, and
installed, which its **Enable** button does. Nothing in this package needs them.
