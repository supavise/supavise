# Supavise v0.4.0

v0.4.0 brings branching on a Supavise server to what hosted Supabase offers. A branch starts with its parent's schema, Edge Functions and saved settings. Studio's merge page shows the schema diff and merges it, and every branch operation is a recorded run with logs. A GitHub App that you create on your server builds a preview branch for each pull request. Studio's AI Assistant works with a model provider and key that you bring. Several dashboard pages that answered with a placeholder now work or refuse with a reason.

This release changes how branches expire, pause and report their status, adds nine registry migrations (1500 to 1550) and moves Studio to patch set 4. Read "Changes in behavior" and "Before you upgrade" first.

## Changes in behavior

### Branches have no lifetime unless you set one

In v0.3.0, a branch expired after 7 days. In v0.4.0, a branch that you make from the dashboard, the API, the CLI or MCP stays until you delete it, as on hosted. A branch that a pull request created lives until the pull request closes. A branch that exists at the upgrade keeps the expiry it has.

To keep a ceiling, set `default_ttl = "7d"` (or another duration) under `[branching]` in `config.toml`, or pass `--ttl 6h` to one `supavise branches create`.

### A branch that nobody uses pauses

On a single server, Supavise pauses a non-persistent branch 30 minutes after its last use. A use is an HTTP request to the branch, a Management API call that runs SQL (the SQL editor, the MCP server's `execute_sql` and `apply_migration`, a migration that the CLI pushes) or a database session that is still connected. This applies to the branches that exist at the upgrade.

The next HTTP request, database connection or Management API call that runs SQL starts the branch. The request waits a few seconds, and a database client may need to connect again. Persistent branches and branches scheduled for deletion aren't paused for idleness, and a branch that you paused yourself stays paused until you resume it. On a cluster of more than one server, Supavise pauses no branch for idleness.

To turn this off, set `[branching] idle_pause_after = "off"`. `idle_wake_timeout_seconds` (60) sets how long a request waits for a start.

### A branch ends at `FUNCTIONS_DEPLOYED`

A create, update, merge or reset ends with the branch at `FUNCTIONS_DEPLOYED`, or at `MIGRATIONS_FAILED` or `FUNCTIONS_FAILED` if it failed. In v0.3.0, a branch ended at `MIGRATIONS_PASSED`, which it passes through while its Edge Functions deploy. If a script waits for `MIGRATIONS_PASSED`, change it to wait for `FUNCTIONS_DEPLOYED`. A branch that finished before the upgrade keeps `MIGRATIONS_PASSED`, and the node treats it as at rest.

### A branch isn't a project of the v1 API

`GET /v1/projects/<branch ref>` and `GET /v1/projects/<branch ref>/branches` answer 404, as they do on hosted. The CLI reads that 404 as "this is not the project to branch from". Read a branch with `GET /v1/branches/<branch ref>`. The other `/v1` project routes still accept a branch ref, and Studio reads a branch through `/platform/projects/<ref>`.

### A branch starts with its parent's schema, functions and settings

In v0.3.0, a branch got the parent's migrations and seed, and its Edge Functions and settings started at their defaults. In v0.4.0, a branch also starts with:

- **The schema of a parent without migrations.** If you built the parent in the SQL editor, the Table Editor or through `execute_sql`, the node reads the parent's schema and runs it on the branch. If that works, the node records it as the parent's first migration, named `remote_schema`, without running it on the parent. A project that has only stock objects gets no such migration.
- **Every Edge Function deployed on the parent.** Function secrets aren't copied.
- **The parent's saved settings.** These are the Auth providers, SMTP, MFA and hook settings, the PostgREST, Storage and Realtime limits, and the Postgres settings that don't size the server. They include the SMTP password and the OAuth provider secrets. If a branch shouldn't use the parent's mail or OAuth accounts, change those settings on the branch.

A branch still gets its own JWT secret, API keys and database password, and it doesn't get the parent's Storage objects. The guide's [What a branch starts with, and what a merge brings back](../guide.md#what-a-branch-starts-with-and-what-a-merge-brings-back) has the rest.

### A reset replays the branch's own migrations

In v0.3.0, a reset rebuilt the branch from the parent. In v0.4.0, it replays the migrations that the branch has recorded: the ones it got from the parent and the ones you added. Tables, rows and other changes that never became migrations are gone. If the node can't read the migration history of a branch that works, the reset stops before it removes anything. To reset from the parent's migrations anyway, run `supavise branches reset --force` or send `?force=true`.

### The `notify_url` body is hosted's envelope and is signed

A branch's `notify_url` receives the body that hosted documents (`type: "run.completed"` and `data.action_run`) with the [Standard Webhooks](https://www.standardwebhooks.com) headers `webhook-id`, `webhook-timestamp` and `webhook-signature`. The fields that v0.3.0 sent at the top level (`branch_id`, `branch_name`, `project_ref`, `parent_project_ref`, `operation`, `status`, `message` and `project_status`) are in a `supavise` object. If a receiver reads them from the top level, change it to read `supavise.<name>`. To verify a signature, use the secret that `supavise branches notify-secret` prints.

### Deleting removes more

- **Files in an S3 bucket.** If Storage runs on S3, deleting a project or a branch, or resetting a branch, empties the project's prefix in the bucket. In v0.3.0, the files stayed.
- **A branch deleted as a project.** `supavise projects delete <branch ref>`, `DELETE /v1/projects/<ref>` and `DELETE /platform/projects/<ref>` on a branch follow the rules of `DELETE /v1/branches/<id>`. A non-persistent branch takes no final backup, and its archive is removed.

### Dashboard pages that answered with a placeholder

- **GitHub.** The GitHub card, the Connections row of your account preferences and "Sync with a GitHub branch" are hidden until the server has a GitHub App. In v0.3.0, a placeholder showed "Connected" to everybody.
- **AI Assistant.** Until you set a provider, the Assistant says "AI provider not set" and its box stays closed. In v0.3.0, it took input and failed on the first message.
- **Refused with a reason.** Switching on image transformation, the **Allow low AAL** switch and similar Auth switches that GoTrue has no equivalent for, the storage archive and backup download of a paused project, changing the email address of a dashboard account, and add-ons other than compute answer 400 with a reason. In v0.3.0, a placeholder answered with a success or left Studio waiting. A project that saved image transformation earlier keeps saving its other storage settings.
- **Hidden.** Supabase Inc.'s legal documents, account deletion and project transfer don't appear.

## What this release adds

### Update, merge, reset, delete and restore like hosted

- **Update branch** (Studio, the MCP server's `rebase_branch`, or `supavise branches push`) brings the parent's new migrations, the parent's schema changes that never became migrations, and its new or changed Edge Functions into the branch. It keeps what the branch added.
- **Merge** (Studio's merge page, the MCP server's `merge_branch`, or `supavise branches merge`) brings the branch's schema changes and Edge Functions into the parent and keeps the branch. On the merge page, Studio shows the SQL the branch changed and records it. The node runs the recorded SQL once on the parent. In the same transaction, it runs what a schema diff doesn't hold from the branch's other migrations: inserted rows, Storage buckets, cron jobs and publication changes. If the branch changed after Studio recorded the SQL, the node ignores the recording and merges the branch's migrations. A merge doesn't move settings, rows you changed outside migrations, Storage objects or function secrets.
- **Diff.** `GET /v1/branches/<id>/diff` returns what the branch changed in its schema, and an empty answer means nothing changed. A Go schema engine in the daemon reads the catalog, so the node needs no Node program for it.
- **Delete and restore.** `supabase branches delete --force=false` (or `DELETE /v1/branches/<id>?force=false`) pauses the branch and deletes it an hour later. **Restore** on the Branches page, or `POST /v1/branches/<id>/restore`, cancels the deletion and starts the branch. A paused branch has **Resume** on its page.
- **Create.** The create body takes `secrets`, which become the branch's Edge Function secrets. `POST /v2/projects/<ref>/branches` works, and a project's default branch can track a Git branch.

### Recorded runs, logs and notifications

Each create, update, merge and reset is one run with seven steps: `clone`, `pull`, `health`, `configure`, `migrate`, `seed` and `deploy`. Studio's **View Logs** lists a branch's runs, and the merge page shows the run of a merge while it works. `supavise branches runs <branch>` lists the runs, and `supavise branches logs <branch> [run-id]` prints a log. The API serves the same data at `GET /v1/projects/<ref>/actions`. The node keeps a run for 30 days. The reason a branch operation failed is in the run's log, in the branch's `supavise_detail` and in `supavise branches get`.

**Close merge request** in Studio, or a successful merge from Studio, the CLI or the MCP server, clears the branch's review mark.

### Custom domains on branches

**Project Settings**, **General**, **Custom domains** works on a branch: the branch claims, verifies and activates a hostname of its own, and the CNAME points at `<branch ref>.api.<domain>`. A branch doesn't inherit its parent's hostname, a reset keeps the branch's hostname (the proxy answers 503 with `Retry-After` while the branch is rebuilt), and deleting the branch frees the hostname and its certificate. A branch with a hostname that has a lifetime raises `branch.expiring` and posts to its `notify_url` a day before it expires. The page is hidden when the node uses `--tls dns01`, which issues only the wildcard certificate.

### GitHub integration

A connected repository gets a preview branch for each pull request, built from the repository's `supabase` directory (migrations, seed, `config.toml` and Edge Functions) and not from your production schema. Supabase's own GitHub App can't send webhooks to your server, so Supavise uses an App that you create:

```bash
sudo -u supavise supavise github app create --owner my-org
```

The command prints a link. Open it in a browser that is signed in to GitHub, confirm the App, install it on your repositories, and then connect a project under **Settings**, **Integrations**, **GitHub**. An App that you already have goes in the `[github]` section of `config.toml`.

- **Pull requests.** Each pull request gets a preview branch, a check named `Supabase Preview` and one comment that the server keeps up to date. A new commit applies the migrations the branch lacks. The branch is deleted when the pull request closes. A pull request from a fork is ignored unless `[github] allow_forks` is `true`.
- **Production.** If you turn on **Deploy to production**, a push to the production branch applies the repository's migrations and Edge Functions to the project, and a check named `Supabase Production` reports it.
- **config.toml.** The sections of `config.toml` that the node can apply become the branch's settings. A `[remotes]` block configures a persistent branch or production.
- **Limits.** `[github] max_concurrent_builds` (3) bounds how many preview branches the node builds at once.
- **A server that GitHub can't reach.** `https://api.<domain>/hooks/github` must be reachable from GitHub. For a server behind NAT, a GitHub Actions workflow in [github-integration.md](../github-integration.md#a-server-github-cannot-reach) does most of the same work with the Supabase CLI.

The guide's [Build a preview branch from every pull request](../guide.md#build-a-preview-branch-from-every-pull-request) and [github-integration.md](../github-integration.md) have the details.

### AI Assistant with a provider you bring

`supavise studio ai set` gives Studio's AI Assistant and the SQL editor's AI features a model provider: OpenAI, or an OpenAI-compatible API such as OpenRouter, LiteLLM, Vercel AI Gateway, Azure OpenAI's v1 endpoint, vLLM or Ollama.

```bash
printf '%s\n' "$OPENROUTER_API_KEY" | sudo -u supavise supavise studio ai set \
  --base-url https://openrouter.ai/api/v1 --api-key-stdin --model anthropic/claude-sonnet-4.5
```

- **The key.** It is stored in a file that only the `supavise` user can read and in Studio's own environment file. It isn't in `config.toml`, in a log, in command output or in an answer of the Management API. Requests go from the server to your provider, and nothing goes to OpenAI unless OpenAI is your provider.
- **The models.** With a gateway, name its models with `--model` (and `--completion-model` for the small calls). Studio sends OpenAI's model names otherwise, and most gateways reject them. `studio ai set` and `studio ai check` warn when you leave `--model` out.
- **The commands.** `studio ai show`, `check` and `clear` complete the set.
- **What the provider sees.** An organization's AI setting controls how much of the database goes to the provider: nothing, the schema, the schema and logs, or the schema, logs and data. Only an Owner changes it. An organization starts with nothing shared, including one that existed before the upgrade.

The guide's [Use the AI Assistant](../guide.md#use-the-ai-assistant) has the rest.

### Audit logs

**Organization settings > Audit Logs** and **Account > Audit Logs** list the requests that changed something: when, who, from which address, which route and which status. Reads, the SQL editor and request bodies aren't recorded. The server keeps 90 days by default (`[api] audit_retention_days`).

### Dashboard pages that work

- **Restore to new project** restores a backup or a point in time as a new project, without the hosted prices and the larger-disk claim. A server without a backup service hides the page.
- **Reset to default** for an email template, **Remove MFA factors** for a user, and the **Data API** pages (the API docs and GraphiQL) work.
- **Create branch** offers **Include data** and shows no hosted prices.
- **Organization settings > SSO** is shown.
- The Edge Function **Test** tab accepts the project's own hosts.

### The Studio crawl in the release gate

A release tag also needs the remote MCP end-to-end job (`mcp-e2e`) and the Studio crawl (`crawl`) to pass on the tagged commit. The crawl opens the pages of the Studio build in a headless browser against a real node. It fails on a placeholder answer, an unexplained 4xx or 5xx, a page or console error, or text that means a dead end.

## Before you upgrade

- **Upgrade as usual** with `sudo supavise upgrade`. It backs up every project first, rolls out with health checks and rolls back on failure. The Studio build changes in this release, so the plan lists Studio among the shared services that move and the dashboard restarts.
- **Two servers.** Run the upgrade on the leader first and then on each follower.
  - A follower that reads a registry the leader hasn't migrated yet shows no GitHub surfaces. Nothing else on it is affected.
  - Upgrade both servers before you use Studio's merge page. An operation that a v0.3.x server runs on a branch doesn't keep the branch's schema base or Edge Function base up to date, so a merge from the dashboard can fail with "already exists" and roll back. It also leaves no action run, so Studio's polls for it get 404.
  - Run `supavise studio ai set` on both servers. The provider belongs to the server, and the server that leads after a failover needs it.
  - If you name an App in `[github]`, use the same section and files on every server that can become the leader.
  - No branch is paused for idleness, and a branch that slept when the second server joined is started again.
- **Rollback needs a registry restore.** Migrations only go forward, so after the upgrade `supavise rollback` refuses until you restore the system cluster from its pre-upgrade base backup, as [the deploy guide](../../deploy/README.md#upgrading-the-node-supavise-upgrade) describes.
- **`config.toml` needs no change.** These sections and keys are optional: `[branching] default_ttl`, `idle_pause_after`, `idle_wake_timeout_seconds` and `expiry_warning_hours`; `[github]`; `[studio.ai]`, which `supavise studio ai set` writes to `config.d/40-studio-ai.toml`; and `[api] audit_retention_days`.
- **Check what your scripts expect.** Look for a wait on `MIGRATIONS_PASSED`, a `notify_url` receiver that reads the old top-level fields, a call to `GET /v1/projects/<branch ref>`, and a reliance on branches that expire after 7 days.
- **To use the GitHub integration**, GitHub's servers must reach `https://api.<domain>/hooks/github`, and the people who connect repositories must reach `https://studio.<domain>`.

## What the upgrade does

1. The new daemon applies registry migrations 1500 to 1550. Seven add tables and two add a column. None changes an existing column.

   | Migration | Adds |
   |---|---|
   | 1500 | The action runs of branches and their steps |
   | 1501 | The Git branch that a project's default branch tracks |
   | 1510 | The schema base of each branch |
   | 1511 | The Edge Function base of each branch |
   | 1520 | Why a project is paused, and which expiry warnings the node sent |
   | 1531 | The audit log |
   | 1540 | The GitHub App, the users' authorizations, the connections, the pull requests that branches follow and the webhook deliveries |
   | 1541 | A column on the branch links of 1540 that records when the seed ran |
   | 1550 | A column on organizations for the AI data-sharing setting |

2. The release changes no pinned version of Postgres, GoTrue, PostgREST, Realtime, Storage or another artifact. Only Studio's patch set changes, from 3 to 4, so Studio runs the build `2026.10.05-sha-94b8b06-p4`. Patches 0005 to 0007 change the branching dialog and the Restore to new project dialogs, point the AI features at your provider, and hide the GitHub surfaces while the server has no App. `supavise upgrade --plan` lists exactly what restarts.
3. The daemon starts to record the audit log and the action runs, and the idle loop begins to pause branches that nobody uses.

## Known gaps

- A Studio merge runs the statements that a schema diff doesn't hold after the diff, in version order. A migration whose later DDL changes what an earlier `INSERT` needs can fail, and the merge then rolls back.
- The schema engine detects no rename: a renamed table shows as a drop and a create. It doesn't model aggregates, operators, casts, rules, range types, collations, extended statistics, inherited tables, column-level privileges, foreign tables and servers, or the event triggers and publications other than the stock ones that every project has. A change to one of them shows in the diff as an unsupported line, and a merge that holds one fails, or with `force` leaves it out.
- A branch that v0.3.x made has no schema base. Its diff compares it with the parent as it is, and lists additions and changes only, until a merge sets a base.
- A database session that opens and closes between two idle checks, such as `psql -c` or a direct `supabase db push` over the database port, isn't noticed as use.
- Nobody has run a Supavisor pooler client against an idle pause. A pooled connection may wake a paused branch again.
- A wake that the node refuses for lack of capacity shows as 503 "waking up" on the proxy and 409 "paused" on the API. The cause is in the log only.
- On a cluster, a branch with data can only be created or reset on the server that holds its parent's data, and a failover doesn't move branches.
- A preview branch applies the sections of `config.toml` that the node can, and names the rest in the run's log. It doesn't apply declarative schemas, and an Edge Function that you remove from the repository stays deployed.
- A seed that fails midway runs again on the next commit, which can repeat effects that aren't atomic.
- The webhook refuses a delivery over 4 MiB with 413. **Resync** deploys production for such a push.
- Studio's GitHub install and authorize windows open github.com, so the dashboard flow works with github.com only.
- The Actions workflow for a server that GitHub can't reach hasn't been run against a node.
- The Assistant can't use the tools that come from the MCP endpoint (documentation search, advisors, logs and the `list_*` tools), and the legacy documentation chat isn't set up.
- `supavise studio ai check` asks the provider for its model list. It doesn't show that the provider serves your model.
- No browser run has loaded **Organization settings > SSO**. If the page is blank or broken, report it.
- On a cluster, the address of a request that enters through a follower can read `127.0.0.1` in the audit log when Edge Functions are enabled.
- The Edge Function **Test** tab fails for a vanity name with a digit or a hyphen, and for a custom hostname.
