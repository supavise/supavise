# Supavise v0.3.0

v0.3.0 brings a server closer to hosted Supabase. The dashboard shows the Security and Performance Advisors and each project's CPU, memory, connections and disk use. Studio can enable Database Webhooks, `supavise logs` reads a project's logs, and a guide moves a project from hosted Supabase and back. A new project also no longer exposes new tables to the Data API until you grant them, as hosted does.

This release changes the Data API defaults of every project, adds two registry migrations and moves GoTrue, Realtime and Storage to newer versions. Read "Changes in behavior" and "Before you upgrade" first.

## Changes in behavior

### New tables are not reachable through the Data API until you grant them

In a project created on v0.3.0, a table you create in `public` isn't reachable through the Data API (REST and GraphQL) until you grant it to `anon`, `authenticated` or `service_role`. A request to `/rest/v1/<table>` answers `42501` (permission denied) until then. The extension `pg_graphql` is off in a new project too. Hosted Supabase made the first change for new projects from 2026-05-30 and the second from 2026-05-18, and it is scheduled to apply the first to its existing projects on 2026-10-30.

Grant each role what it needs, then turn on row level security. A migration written this way runs unchanged on hosted Supabase:

```sql
create table public.todos (id bigint generated always as identity primary key, title text not null);
grant select on public.todos to anon;
grant select, insert, update, delete on public.todos to authenticated;
grant all on public.todos to service_role;
alter table public.todos enable row level security;
```

If a project must keep the old behavior from its creation, check **Automatically expose new tables** in the dashboard, pass `--expose-new-tables` to `supavise projects create`, or send `data_api_revoke_default_privileges: false` to `POST /platform/projects`.

**Existing projects.** When a node upgrades to v0.3.0, Supavise revokes the default privileges of the role `postgres` in `public` once for every existing project, as hosted is scheduled to do on 2026-10-30. Tables that exist keep their grants and keep answering. A table created after the upgrade without a grant isn't reachable through the Data API.

- **When it runs.** The change starts after the upgrade ends. A project whose database is down or busy is tried again after 5 minutes, then after 15 minutes, then every hour. A paused project gets it when it resumes. Supavise doesn't run it while an upgrade runs, including a rollback.
- **What it changes.** It revokes the grants that new tables, sequences and functions in `public` would get for `anon`, `authenticated` and `service_role`. A table that another role creates keeps the grants that role's defaults give. New functions stay executable by everyone (`public`), as on hosted, because PostgreSQL doesn't let a per-schema default privilege take that grant away. To limit a function to signed-in users, run `revoke execute on function public.my_function() from public, anon;`.
- **Branches and restores.** A branch follows its parent's choice. A restore as a new project follows its backup, so a backup taken before the upgrade gets the revoke at the new project's first pass. A restore in place follows its backup too: the project's recorded choice is set from the backup, and a backup taken before the upgrade gets the revoke once, right after the restore.
- **Rollback.** To bring the old behavior back for a project, run this SQL as `postgres`. The first block restores the defaults for new objects, and the second grants the objects created since the change:

  ```sql
  alter default privileges for role postgres in schema public grant select, insert, update, delete on tables to anon, authenticated, service_role;
  alter default privileges for role postgres in schema public grant usage, select on sequences to anon, authenticated, service_role;
  alter default privileges for role postgres in schema public grant execute on functions to anon, authenticated, service_role;
  alter default privileges for role postgres in schema public grant execute on functions to public;
  ```

  ```sql
  grant select, insert, update, delete on all tables in schema public to anon, authenticated, service_role;
  grant usage, select on all sequences in schema public to anon, authenticated, service_role;
  grant execute on all functions in schema public to anon, authenticated, service_role;
  ```

  Supavise records its decision in the registry, not in your database, so after you roll back with SQL no restart and no later upgrade revokes the defaults again.

The guide's section [New tables need a grant](../guide.md#new-tables-need-a-grant) has the rest, including the `api` schema and exposed-schema options of a create.

**GraphQL.** In a new project, `/graphql/v1` answers that `pg_graphql` isn't enabled until you turn it on under **Database**, **Extensions**, or run `create extension pg_graphql;`. A project that has the extension keeps it.

### Pages that depend on logs show an error

A server has no log store for the dashboard. The Logs pages, the reports that read logs and the MCP server's log tools answer with an error that names `supavise logs <ref>`, instead of an empty list that reads as "no errors".

### Calls a server can't serve answer with a reason

A placeholder used to answer these calls with a body that Studio read as success or as an empty result. They now answer with an error and a reason, which the dashboard shows: adding a Third-party Auth provider, creating or migrating JWT signing keys, SSL enforcement, feedback, the Auth overview's metrics and `PUT /v1/projects/<ref>/pgsodium`. Third-party Auth stays in the dashboard menu. The Database report's `infra-monitoring` call answers 400 for a metric name outside hosted's list of 57, where it used to answer a chart for any name.

## What this release adds

### Advisors

Studio's **Security Advisor** and **Performance Advisor** pages, the advisor panel of the project home, `supabase db advisors` and the MCP server's `get_advisors` list problems in a project's schema and settings ([guide](../guide.md#check-a-project-with-the-advisors)).

- **The checks.** Supavise runs the database checks that Studio runs in its own self-hosted mode, in the project's own database, when you ask. It keeps a result for 10 seconds and clears it after a migration or a statement that changes the schema through the Management API. The checks stop after 30 seconds.
- **Settings findings.** Supavise reports four findings from the Auth settings, with hosted's names: leaked password protection turned off (`auth_leaked_password_protection`), fewer than two MFA methods (`auth_insufficient_mfa_options`), an email OTP that lives longer than an hour (`auth_otp_long_expiry`) and an Auth connection pool set in connections (`auth_db_connections_absolute`). Hosted may show the first two only on some plans; Supavise reports them whenever the setting is off.
- **One-hour email OTP.** A new project starts with an email OTP that expires after an hour, as a new hosted project does. A project made before v0.3.0 keeps its expiry of a day, so its Security Advisor shows `auth_otp_long_expiry` until you shorten it under **Authentication > Sign In / Providers > Email**.
- **Rules.** If you turn on the **Disable Advisor rules** feature preview in Studio, Owners and Administrators can disable a check for the whole project.

### Usage reports, resource warnings and alerts

Studio's **Observability > Database** report, its overview cards and the **Compute and Disk** page show CPU, memory, connections, disk size and the block reads and writes of Postgres for each project. The server measures them once a minute, keeps the minutes of the last 3 days and the hours of the last 92, and needs about 1 MiB of disk for each project.

- **Resource warnings.** Studio shows its warning above a project at 80% of its disk quota or CPU quota, or 85% of its memory limit. The warning is critical at 90% (95% for memory), and for 15 minutes after the kernel kills a process of the project for lack of memory.
- **Alerts.** `memory_low` fires when less than 10% of the server's memory is available, or when programs wait for memory while less than 30% is available. `project_disk_high` fires at 80% of a project's disk quota and again at 90%. Both go to the `[alerts]` destinations you set.
- **Requirements.** The measurements need Linux with control groups v2, as on Ubuntu 24.04 and Debian 12. The disk warnings and `project_disk_high` need the XFS data volume with project quotas that the CloudFormation template sets up.

### Request counts on the project home

The request chart of the project home counts the requests that the server's proxy served to the project's REST, Auth, Storage and Realtime APIs, by minute, hour or day. The counts live in memory and cover the requests that this server served.

### Database Webhooks

In Studio, **Integrations**, **Database Webhooks**, **Enable webhooks** creates the `supabase_functions` schema and turns on `pg_net` in the project. A webhook then sends an HTTP request when a row is inserted, updated or deleted, and the response is in `net._http_response`.

- If you created a schema named `supabase_functions` yourself, **Enable webhooks** fails with a message. Drop or rename your schema first.
- Enabling runs no code that a project wrote with superuser rights.
- A branch created with data sends no webhook requests to the network unless you created it with `--allow-egress`.

### `supavise logs` and log pages that say what they lack

`sudo supavise logs <ref>` prints the last 100 lines of everything a project writes, from the systemd journal. `--service` picks one of `postgres`, `auth`, `rest`, `realtime`, `storage`, `pooler` and `functions`, `-n` sets the number of lines, `--since` takes an age or a time, and `-f` keeps printing. When a project has no lines on the server, the hint says to run the command on the server that hosts the project, and on a cluster the dashboard's message names that server.

### Move a project from hosted Supabase, and the legacy JWT secret

The guide's [Move a project from hosted Supabase](../guide.md#move-a-project-from-hosted-supabase) moves the database with its Auth users, the files in Storage, the Edge Functions, the settings and the keys your app holds, and [Move a project off Supavise](../guide.md#move-a-project-off-supavise) goes the other way. The hosted project keeps running until you switch your app.

- **Keys.** `supavise projects create` takes `--jwt-secret-file`, and with it `--anon-key-file` and `--service-role-key-file`, so a project keeps the legacy `anon` and `service_role` keys that your app holds. The `sb_` keys are new.
- **The legacy JWT secret.** **Project settings**, **JWT keys**, **Legacy JWT secret**, **Change legacy JWT secret** works: it signs the `anon` and `service_role` keys again with a random secret or your own, restarts the services that verify them, including the PostgREST of the project's read replicas on their own servers, and updates the Edge Functions' environment. If the change fails and Supavise can't put the previous secret back, the API and the CLI say so and point to `supavise projects health <ref>`. A read replica that can't be updated doesn't undo the change: the dashboard names it, and it refuses the new keys until you restart it or save the same secret again.
- **Restore.** The guide's restore revokes the node's default privileges inside its transaction, so a table you locked down on hosted stays locked down. A grants comparison at the end shows any difference. It also comments out the privileges on configuration parameters that the role dump lists, because the `postgres` role can't grant them.
- **Vault.** The dumps leave the Vault and pgsodium schemas out, so create Vault secrets again with `vault.create_secret`. `GET /v1/projects/<ref>/pgsodium` returns the project's root key, and `PUT` is refused with an explanation because Supavise doesn't replace the key of a running cluster.

## Before you upgrade

- **Upgrade as usual** with `sudo supavise upgrade`. It backs up every project first, rolls out with health checks and rolls back on failure. The Studio build doesn't change in this release.
- **Two servers.** Run the upgrade on the leader first and then on each follower. The release adds registry migrations, and a follower reports its projects' measurements to the leader only from v0.3.0 on, so Studio's reports for a project may show nothing until its server runs v0.3.0. A project that you create on a follower still on the previous release goes without the revoke, with a warning, and gets it after that follower upgrades.
- **Rollback needs a registry restore.** Migration 1400 adds the per-project Data API choice (`supavise.project_data_api`) and 1450 adds the Advisor rules (`supavise.advisor_exceptions`). Migrations only go forward, so after the upgrade `supavise rollback` refuses until you restore the system cluster from its pre-upgrade base backup, as [the deploy guide](../../deploy/README.md#upgrading-the-node-supavise-upgrade) describes. That restore doesn't undo the Data API revoke in your project databases, so tables created after a rollback stay closed to the Data API until you run the grant statements in the guide's [New tables need a grant](../guide.md#new-tables-need-a-grant). The revoke waits for a day after an upgrade that ends as failed, which gives you time to choose between fixing forward and a rollback.
- **Projects keep the newer migrations after a rollback.** GoTrue, Realtime and Storage run their new migrations in each project's database, and a rollback leaves them there. The older GoTrue runs on the newer schema. A Storage release older than v1.80.0 finds every migration it knows already recorded, runs none, sets the tenant's recorded migration version back and refreshes two stored hashes. The pre-upgrade backup is the way back for the data.
- **`config.toml` needs no change.** The optional setting `[health] memory_low_percent` (default 10, at most 90) sets the line for `memory_low`. Each server raises `memory_low` and `project_disk_high` for the projects it runs, so in a cluster set the `[alerts]` destinations on every server.
- **Check what your apps and migrations expect.** If a script or migration creates tables in `public` and relies on the automatic grants, add the grants to it, or run the rollback SQL above after the upgrade.

## What the upgrade does

1. The new daemon applies registry migrations 1400 and 1450. Both add a table and change none that exists.
2. The rollout updates the shared services, Realtime and Storage, one at a time, then the projects: one canary first, then batches of five, with a health check after each. GoTrue moves with its project, and a project that restarts drops its connections briefly. GoTrue, Realtime and Storage run their new migrations in each project's database after they start on the new versions.
3. When the upgrade ends, the daemon runs the revoke in each existing project once. It doesn't run again for a project that has a recorded choice.
4. The daemon starts measuring each project once a minute, and Studio's reports fill from then on.

## Known gaps

- The dashboard has no log store. The Auth, Edge Functions and some other report charts can't show an error, so they stay empty.
- `supavise logs` reads the journal of the server it runs on, and Auth, REST, Realtime and Storage log warnings and errors only, so a healthy project prints little from them.
- The Advisors don't report the health checks, which need logs and metrics, the compliance checks (for example SSL enforcement and point-in-time recovery) or the Postgres security-patch check. Supavise has no record of when hosted reports them.
- The charts for network traffic, the disk I/O budget, memory commitment, PgBouncer and Realtime have no source on a server and stay at zero.
- Without an XFS data volume with project quotas, the disk figures are the volume's, and Studio shows no quota warning.
- An OOM kill that systemd restarts counts once for each restart, which makes the count a lower bound. A kill in one project can also show for another project that restarted in the same minute.
- The request counts start at zero when `supavise` restarts, and on a cluster they leave out the requests that the second server served.
- Third-party Auth providers and JWT signing keys aren't supported. A project signs its tokens with the legacy JWT secret.
- The new GoTrue settings for MFA recovery codes and email identities aren't in the Management API.
- A move from hosted doesn't carry the `sb_` keys, Vault secrets, the pgsodium key, passwords of your own login roles, secret values or the access tokens that hosted signed with an asymmetric key.
- `supavise projects rotate-keys` can't reach other servers, so it prints the new keys and then names the read replicas to restart. A replica whose server was away when the secret changed keeps the previous secret until you restart it or save the project's current secret again in the dashboard.
- The guide's two hosted API calls for the legacy JWT secret and the legacy keys haven't been run against a hosted project. The dashboard shows both values.
- The Storage rollback behavior comes from reading upstream's source at v1.79.36, v1.80.0 and v1.81.0. Nobody has run an older Storage against a v1.81.0 tenant database.
